# 性能评估报告

应用栈：Express 4 + mysql2 + React 19 + Vite 6 + Tailwind 4。我从后端、数据库、前端三个维度做了完整评估，**最大的瓶颈是后端的 N+1 查询模式**，下面按严重程度排序。

---

## 一、后端严重问题（P0，立即修复）

### 1. N+1 查询遍布列表接口（最关键）

几乎所有列表接口都用 `Promise.all + map` 对每条记录再发多次查询，会随数据量线性放大。

**`GET /api/assignments`** — [assignments.ts:14-31](file:///Users/dgjin/Documents/Codex/2026-07-22/cong/free-report/server/src/routes/assignments.ts#L14-L31)
每条任务查 4 次（template/company/user/latestSubmission）。50 条任务 = 200+ 次查询。

**`GET /api/templates`** — [templates.ts:40-51](file:///Users/dgjin/Documents/Codex/2026-07-22/cong/free-report/server/src/routes/templates.ts#L40-L51)
每个模板查 2 次（fields + creator）。

**`GET /api/aggregations/by-template/:templateId`** — [aggregations.ts:79-143](file:///Users/dgjin/Documents/Codex/2026-07-22/cong/free-report/server/src/routes/aggregations.ts#L79-L143)
每个目标机构 2 次查询（latestSubmission + submissionData），并且**先 `getAssignments()` 和 `getCompanies()` 把全表拉回来再在 JS 里过滤**。

**`GET /api/aggregations/history/:templateId`** — [aggregations.ts:190-214](file:///Users/dgjin/Documents/Codex/2026-07-22/cong/free-report/server/src/routes/aggregations.ts#L190-L214)
嵌套 N+1：assignment → company + 每条 submission → submitter。还调用 `getSubmissions()` 把全表 submissions 拉回来。

**`GET /api/submissions/:id`** — [submissions.ts:165-172](file:///Users/dgjin/Documents/Codex/2026-07-22/cong/free-report/server/src/routes/submissions.ts#L165-L172)
每条审批记录单独 `getUserById`。

> **改法**：用 JOIN 改写为单条 SQL，或在 `Database` 层加批量方法（`getCompaniesByIds`、`getUsersByIds`、`getLatestSubmissionsByAssignmentIds`）一次 `IN (...)` 取回后在内存里组装。

### 2. 认证中间件每个请求 2 次 DB 查询
[auth.ts:89-107](file:///Users/dgjin/Documents/Codex/2026-07-22/cong/free-report/server/src/auth.ts#L89-L107)
每个受保护接口都跑 `getUserById` + `getCompanyById`。这意味着任何一个列表接口的实际 DB 调用数还要 +2。

> **改法**：JWT 已包含 `company_name/company_code/company_level/role`，可改成「信任 token + 短 TTL 内存缓存（如 30 秒 LRU）」，仅在 `decoded.exp` 即将过期或显式刷新时回查 DB。

### 3. 同步 bcrypt 阻塞事件循环
[server.ts:59](file:///Users/dgjin/Documents/Codex/2026-07-22/cong/free-report/server.ts#L59)
`bcrypt.compareSync` 是 CPU 密集同步调用，会阻塞所有其他请求。

> **改法**：换成 `await bcrypt.compare(password, hash)`。

### 4. 写入路径的循环 INSERT
[db.ts:364-368](file:///Users/dgjin/Documents/Codex/2026-07-22/cong/free-report/server/src/db.ts#L364-L368) `createOrUpdateSubmission` 一行一行插入 `report_submission_data`；[db.ts:161-168](file:///Users/dgjin/Documents/Codex/2026-07-22/cong/free-report/server/src/db.ts#L161-L168) `createTemplate` 同样；[db.ts:270-287](file:///Users/dgjin/Documents/Codex/2026-07-22/cong/free-report/server/src/db.ts#L270-L287) `createAssignments` 顺序 INSERT IGNORE + SELECT。

> **改法**：用一条 `INSERT ... VALUES (?,?,?,?),(?,?,?,?)...` 批量插入。

### 5. 缺少关键索引
查看 [sql/001_schema.sql](file:///Users/dgjin/Documents/Codex/2026-07-22/cong/free-report/sql/001_schema.sql) 与实际查询对比，缺以下索引：

| 缺失索引 | 用于 |
|---|---|
| `report_templates(owner_department_id)` | `getTemplatesByDepartment` |
| `report_assignments(template_id)` | `getAssignments` 的 template 过滤、history 接口 |
| `report_assignments(issuer_department_id)` | `getPendingReceipts` |
| `report_submissions(submitted_by_company_id)` | `getPendingApprovalsForUser`、`canReadSubmission` |
| `report_submissions(submitted_by)` | history 接口 |

### 6. 全表扫描式查询
- `getAssignments()` ([db.ts:255-257](file:///Users/dgjin/Documents/Codex/2026-07-22/cong/free-report/server/src/db.ts#L255-L257))、`getSubmissions()` ([db.ts:297-299](file:///Users/dgjin/Documents/Codex/2026-07-22/cong/free-report/server/src/db.ts#L297-L299))、`getCompanies()` ([db.ts:75-77](file:///Users/dgjin/Documents/Codex/2026-07-22/cong/free-report/server/src/db.ts#L75-L77)) 都是 `SELECT *` 全表，再由路由层在 JS 里过滤。

## 二、后端中等问题（P1）

### 7. 无响应压缩
[server.ts](file:///Users/dgjin/Documents/Codex/2026-07-22/cong/free-report/server.ts) 没有挂 `compression` 中间件，汇总接口的 JSON 响应（含明细行）经常几十 KB 起步，未压缩直传。

```bash
bun add compression @types/compression
```
```ts
import compression from 'compression';
app.use(compression());
```

### 8. 连接池偏小
[mysql.ts:31](file:///Users/dgjin/Documents/Codex/2026-07-22/cong/free-report/server/src/mysql.ts#L31) `connectionLimit: 10`。在 N+1 放大下，10 个并发用户就可能出现连接排队。先把 N+1 修了再考虑升到 20–30。

### 9. JSON body 限制过大
[server.ts:40](file:///Users/dgjin/Documents/Codex/2026-07-22/cong/free-report/server.ts#L40) `limit: '10mb'` 偏大，可能造成内存压力。除 Excel 导入接口外，其它接口建议 1MB。

### 10. dev 模式跑 tsx
[package.json:7](file:///Users/dgjin/Documents/Codex/2026-07-22/cong/free-report/package.json#L7) `"dev": "node --import tsx server.ts & npx vite"`。tsx 是 JIT 转译，比 `dist/server.cjs` 慢不少。如果"应用运行较慢"是在开发环境测的，先确认是不是 tsx 的开销。

## 三、前端问题（P1）

### 11. 无路由级代码分割
[App.tsx:1-15](file:///Users/dgjin/Documents/Codex/2026-07-22/cong/free-report/src/App.tsx#L1-L15) 11 个页面全部同步 import，首屏加载整个 bundle。

> **改法**：
```tsx
const Dashboard = React.lazy(() => import('./pages/Dashboard'));
// ... 用 <Suspense fallback={...}> 包裹
```

### 12. 重型依赖未拆 chunk
`xlsx`、`@google/genai`、`motion` 都进了主 bundle，但只有少数页面用到。[vite.config.ts](file:///Users/dgjin/Documents/Codex/2026-07-22/cong/free-report/vite.config.ts) 没配 `manualChunks`。

```ts
build: { rollupOptions: { output: { manualChunks: {
  xlsx: ['xlsx'], genai: ['@google/genai'], motion: ['motion'],
} } } }
```

### 13. 无客户端数据缓存
[api.ts](file:///Users/dgjin/Documents/Codex/2026-07-22/cong/free-report/src/services/api.ts) 是裸 `fetch`，每次路由切换都重新拉取 templates/assignments。建议引入 SWR 或 TanStack Query，至少对 `getTemplates`、`getCompanies`、`getAssignments` 做缓存。

### 14. AggregationView 副作用链可能重复请求
[AggregationView.tsx:24-26](file:///Users/dgjin/Documents/Codex/2026-07-22/cong/free-report/src/pages/AggregationView.tsx#L24-L26) 三个 useEffect 互相依赖 `selectedTemplateId`/`selectedPeriod`/`periods`，初始挂载时 `loadAggregation` 容易被触发两次。建议合并成单个 effect 或用 `useMemo` 派生 periods 后再决定是否加载。

## ADR：是否将后端从 Express/TypeScript 迁移到 Spring Boot

**Status**: Rejected（建议维持现状）

### Context（背景）

当前架构（来自 [README.md:3](file:///Users/dgjin/Documents/Codex/2026-07-22/cong/free-report/README.md#L3) 与代码）：
- 前端：React 19 + Vite 6 + Tailwind 4
- 后端：Express 4 + mysql2 + TypeScript（dev 用 tsx，prod 用 esbuild 打成单文件 `dist/server.cjs`）
- DB：MySQL 8
- 部署形态：**本地/内网私有化运行**，单实例

应用规模（实测）：
- 后端代码：1 个 `server.ts` + 8 个路由文件 + `db.ts`（510 行）+ 4 个领域模块
- 前后端共用类型：[src/types.ts](file:///Users/dgjin/Documents/Codex/2026-07-22/cong/free-report/src/types.ts)
- 测试：18 个 `node:test` 文件
- 业务复杂度：中等（报表模板/下发/填报/审批/签收/汇总）

上一轮分析定位的"应用运行较慢"根因：
1. N+1 查询遍布 4 个列表接口
2. 认证中间件每请求 2 次 DB 查询
3. 缺失索引
4. 同步 `bcrypt.compareSync` 阻塞事件循环
5. 循环 INSERT
6. 前端无代码分割

**这些都不是 Express 框架的问题，而是数据访问模式和数据库设计问题。**

### Decision

维持 Express + TypeScript，优先修上一轮列出的 P0/P1 项。暂不迁移 Spring Boot。

### Alternatives Considered

| 维度 | 留在 Express（推荐） | 迁移 Spring Boot | 迁移到 NestJS（折中） |
|---|---|---|---|
| **能否解决当前性能问题** | 能（修 N+1 + 索引即可） | **不能**——同样会写出 N+1，JPA 甚至更容易触发 lazy-load N+1 | 能 |
| **重写成本** | 0 | 高（~1500 行业务逻辑 + 18 个测试全部重写） | 中（同语言，可渐进迁移） |
| **类型共享** | 已有，[src/types.ts](file:///Users/dgjin/Documents/Codex/2026-07-22/cong/free-report/src/types.ts) 前后端共用 | **丢失**——Java/TS 之间需手动同步契约 | 保留 |
| **运行时内存** | ~80–150MB | ~400–800MB（JVM） | ~80–150MB |
| **冷启动** | <1s | 5–30s（对私有化部署的频繁重启不友好） | <1s |
| **开发迭代速度** | tsx JIT，秒级热重载 | 编译 + JVM 启动，10s+ | 秒级 |
| **运维复杂度** | 单 cjs 文件 + Node | JVM + JAR + GC 调优 | 单文件 + Node |
| **团队技能匹配** | 现有 React/TS 栈一致 | 需要招/学 Java 团队 | 现有栈一致 |
| **私有化部署友好度** | 高（一个二进制 + MySQL） | 中（JVM 占内存，客户机器配置要求更高） | 高 |
| **长期可维护性** | 中等规模够用 | 大团队/大规模更优 | 中等规模够用 |

### Consequences（迁移到 Spring Boot 的后果）

**正向**
- JPA/Hibernate 减少手写 SQL 样板
- Spring Security 成熟，权限注解化
- Actuator/Micrometer 自带监控
- 编译期类型检查更严
- 如果未来要招大团队，Java 人才池更大

**负向**
- **解决不了当前慢的根因**——JPA 不当使用反而更容易产生 N+1（`@OneToMany` lazy fetch 是经典坑）
- 全部业务逻辑重写：`submission-workflow`、`template-lifecycle`、`department-policy`、`createOrUpdateSubmission` 的事务逻辑等
- 18 个测试全部用 JUnit 重写
- 前后端类型契约断裂，需引入 OpenAPI 或重复维护 DTO
- 私有化客户机器内存需求翻 3–5 倍
- 构建链从 `esbuild`（毫秒级）变成 Maven/Gradle（分钟级）
- 与现有 Vite 前端的 proxy 配置、dev 工作流都要重做

### Trade-offs

迁移 Spring Boot 的唯一实质收益是「企业级生态 + 大团队可维护性」，但当前应用：
- 规模不到需要 JPA 的程度（[db.ts](file:///Users/dgjin/Documents/Codex/2026-07-22/cong/free-report/server/src/db.ts) 510 行手写 SQL 反而更清晰可控）
- 是**私有化单实例部署**，不享受 Spring Boot 的水平扩展优势
- 团队已是 TS 全栈，迁移会割裂技能栈

**用 3–6 个月重写换不来性能提升**，是把工程问题误判成语言问题。

```
经办人提交 → pending_review（创建复核人审批记录）

    ↓
审批人审批 → pending_receipt（发送至部门签收）
    ↓
部门签收   → received（完成）
```

## B. 审批流状态机

### 双重状态机

系统有**两个并行状态字段**：`assignment.status` 和 `submission.status`，它们的值不完全一致，容易造成混乱。

#### Assignment 状态流转

```
pending → filling → submitted → pending_receipt → received
                ↘ (rejected) ↙       ↘ (returned) ↙
                     rejected          returned
                                            ↘ filling (重新填报)
                 approved / aggregated (终态)
```

#### Submission 状态流转（三级审批）

```
draft → pending_review → pending_approval → pending_receipt → received
  ↗(rejected)     ↙(rejected)        ↙(rejected)
  draft           rejected           rejected
  ↗(returned)                           ↙(returned)
  draft                                 returned → draft
```

## F. 改进建议（按优先级）

### 建议 1（P0）：修复审批权限漏洞

**问题**：`branch_admin` 和 `super_admin` 可审批所有级别

**方案**：修改 `getPendingApprovalsForUser`，严格按角色匹配审批级别

```typescript
// db.ts getPendingApprovalsForUser
WHERE ar.status='pending' AND s.submitted_by_company_id=? AND
  ((?='reviewer' AND ar.approval_level='reviewer') OR
   (?='approver' AND ar.approval_level='approver'))
// 移除 branch_admin 和 super_admin 的绕行
```

同时修改 `canWriteAssignment`，移除 `department_report_admin`：

```typescript
// department-policy.ts
export function canWriteAssignment(user, assignment) {
  if (isSuperAdminReadOnly(user) || user.company_id !== assignment.assigned_to_company_id) return false;
  return ['handler', 'branch_admin'].includes(user.role); // 移除 department_report_admin
}
```

### 建议 2（P0）：清理驳回后重新提交的旧审批记录

**问题**：驳回后重新提交，旧版本的 pending approval records 仍然存在

**方案**：在 `createOrUpdateSubmission` 创建新版本前，关闭旧版本的所有 pending records

```typescript
// 在创建新版本前
if (existing && ['rejected', 'returned'].includes(existing.status)) {
  await connection.execute(
    "UPDATE approval_records SET status='rejected', comment='版本过期（重新提交）' WHERE submission_id=? AND status='pending'",
    [existing.id]
  );
}
```

### 建议 3（P1）：统一状态机，移除死状态

**问题**：`approved` 状态无代码路径可达，`headquarter_admin` 是僵尸角色

**方案**：
- 从 `AssignmentStatus` 和 `SubmissionStatus` 中移除 `approved`
- 从 `Role` 中移除 `headquarter_admin`
- 清理所有引用这两个值的代码（前端 statusMap、classifyAssignment 等）
- `classifyAssignment` 的 `completed` 桶只检查 `received` 和 `aggregated`

### 建议 4（P1）：修复逾期判断

**问题**：`submitted` 状态（已提交待复核/审批）不应显示逾期

**方案**：

```typescript
// Dashboard.tsx:215
const isOverdue = new Date(item.deadline) < new Date() 
  && !['approved', 'aggregated', 'received', 'pending_receipt', 'submitted'].includes(item.status);
```

### 建议 5（P2）：升级 ReceiptCenter 交互

**问题**：签收中心使用 `prompt()`，无法查看填报详情

**方案**：参照 ApprovalList 的弹窗模式，增加签收详情弹窗，显示汇总指标 + 明细数据 + 退回原因输入框

### 建议 6（P2）：拆分 Dashboard 为 HQ 和 Branch 两个组件

**问题**：大量 `isHQ ? A : B` 三元表达式

**方案**：

```
Dashboard/
├── index.tsx          — 路由分发
├── HqDashboard.tsx    — 总部工作台（模板/任务/分公司统计）
└── BranchDashboard.tsx — 分公司工作台（任务/审批/填报统计）
```

### 建议 7（P2）：优化 ReportFill 提交后体验

**问题**：提交后无引导

**方案**：提交成功后显示一个成功页/Toast，提供两个选项：
- "返回工作台" → navigate('/')
- "查看提交详情" → 留在当前页切换为只读模式

### 建议 8（P2）：AggregationView 合并 useEffect

**问题**：三个 useEffect 链可能导致重复请求

**方案**：合并为一个 effect，用 `useMemo` 派生 periods

```typescript
const periods = useMemo(
  () => Array.from(new Set(assignments.filter(a => a.template_id === selectedTemplateId).map(a => a.period_label))).sort().reverse(),
  [assignments, selectedTemplateId]
);
const effectivePeriod = periodParam && periods.includes(periodParam) ? periodParam 
  : (periods.includes(selectedPeriod) ? selectedPeriod : periods[0] || '');

useEffect(() => {
  if (selectedTemplateId && effectivePeriod) loadAggregation(selectedTemplateId, effectivePeriod);
}, [selectedTemplateId, effectivePeriod]);
```

### 建议 9（P3）：无复核人时的降级策略

**问题**：无复核人直接跳到 pending_receipt，跳过审批

**方案**：改为查找 approver，如果有 approver 则直接进入 pending_approval；如果都没有才直接 pending_receipt

```typescript
if (isSubmit) {
  reviewer = await first<User>(connection,
    "SELECT * FROM users WHERE company_id=? AND role='reviewer' AND status='active' ORDER BY id LIMIT 1", [companyId]);
  const approver = await first<User>(connection,
    "SELECT * FROM users WHERE company_id=? AND role='approver' AND status='active' ORDER BY id LIMIT 1", [companyId]);
  
  if (reviewer) {
    initialStatus = 'pending_review';
    assignmentStatus = 'submitted';
  } else if (approver) {
    initialStatus = 'pending_approval';
    assignmentStatus = 'submitted';
    // 直接创建 approver 审批记录
  } else {
    initialStatus = 'pending_receipt';
    assignmentStatus = 'pending_receipt';
  }
}
```
