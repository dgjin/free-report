## 1. 系统概述

### 1.1 系统定位

自由报表（FreeReport）是一套面向企业总部-部门-分公司三级组织架构的报表填报与审批系统。核心能力包括：

- **模板设计**：支持文本、数字、日期、下拉选择、多行文本及二维交叉表字段
- **周期下发**：按模板向指定分公司下发填报任务，支持一次性下发
- **三级审批**：经办人填报 → 复核人审核 → 审批人终审 → 发起部门签收
- **强制收回**：发起部门可强制收回已下发的任务
- **智能汇总**：多机构数据横向对比，支持 Excel 导出
- **部门隔离**：严格的部门级数据访问控制

### 1.2 组织模型

```
总部 (headquarter)
├── 业务综合管理部 (department)
├── 办公室 (department)
├── 风险管理部 (department)
│   ├── 北京分公司 (branch)
│   └── 上海分公司 (branch)
└── ...
```

### 1.3 角色矩阵

| 角色 | 填报 | 审批 | 模板管理 | 下发 | 签收 | 汇总查看 | 机构管理 |
|------|:----:|:----:|:--------:|:----:|:----:|:--------:|:--------:|
| 超级管理员 | - | - | 只读 | - | - | 只读 | ✓ |
| 部门报表管理员 | - | - | ✓ | ✓ | ✓ | ✓ | - |
| 分公司管理员 | ✓ | - | - | - | - | - | - |
| 经办人 | ✓ | - | - | - | - | - | - |
| 复核人 | - | ✓ | - | - | - | - | - |
| 审批人 | - | ✓ | - | - | - | - | - |

## 4. 后端架构

### 4.1 数据访问层

`Database` 类（`server/src/db.ts`）封装全部 MySQL 操作，核心设计：

- **事务封装**：`transaction(fn)` 自动 begin/commit/rollback/release
- **悲观锁**：`lockWritableTemplate()` 使用 `SELECT ... FOR UPDATE` 防并发冲突
- **批量查询**：`getXxxByIds()` + Map 关联，消除 N+1 查询
- **SQL 级过滤**：聚合/历史端点在 SQL 层按条件过滤，避免全表加载

主要方法分类：

| 类别 | 方法 |
|------|------|
| 机构 | getCompanies, createCompany, disableCompany, getAssignmentTargets |
| 用户 | getUsers, getUserByUsername, updateUserOrganizationRole |
| 模板 | getTemplatesForUser, createTemplate, setTemplateEnabled, addMatrixFields |
| 下发 | createAssignments(isOneTime), recallAssignment, getAssignmentsForUser |
| 填报 | createOrUpdateSubmission, getSubmissionData |
| 审批 | getPendingApprovalsForUser, processApprovalAction |
| 签收 | getPendingReceipts, processReceipt |
| 汇总 | aggregateAssignment, getLatestApprovedSubmissionsByAssignmentIds |

### 4.2 认证中间件

- **JWT 鉴权**：24h 有效期，Bearer token
- **内存缓存**：30 秒 TTL，避免每请求重复查库
- **角色守卫**：requireHeadquarter / requireDepartmentReportAdmin / requireSuperAdmin / requireRole(...roles)
- **缓存失效**：用户状态变更时主动清除缓存

### 4.3 部门隔离策略

`department-policy.ts` 实现严格的数据访问控制：

| 操作 | 超管 | 部门管理员 | 分公司用户 |
|------|:----:|:--------:|:--------:|
| 读模板 | ✓ 全部 | ✓ 本部门 | - |
| 管理模板 | - | ✓ 本部门 | - |
| 读任务 | ✓ 全部 | ✓ 本部门发起 + 被下发 | ✓ 本机构被下发 |
| 写任务 | - | - | ✓ handler/branch_admin |
| 签收 | - | ✓ 本部门 | - |

### 4.4 业务状态机

**模板生命周期**：`draft → published ↔ archived`

**填报状态机**：`draft → pending_review → pending_approval → pending_receipt → received`

**可写状态判定**（`submission-workflow.ts`）：仅 `undefined` / `draft` / `returned` / `rejected` 可保存或提交。

## 6. 核心业务流程

### 6.1 三级审批 + 签收流程

```
经办人填报并提交
    │
    ▼
┌─ 有复核人？─┐
│ 是          │ 否
▼             ▼
pending_review    pending_receipt（跳过内部审批）
    │                 │
    ▼                 │
复核人通过             │
    │                 │
    ▼                 │
pending_approval       │
    │                 │
    ▼                 │
审批人通过             │
    │                 │
    └─────► pending_receipt
                  │
                  ▼
            发起部门签收
                  │
          ┌───────┴───────┐
          ▼               ▼
        received      returned（退回）
```

**驳回/退回**：任意审批环节可驳回，状态变为 `rejected` 或 `returned`，经办人可修改后重新提交。

### 6.2 强制收回流程

```
发起部门管理员 → 选择未汇总任务 → 填写收回原因 → 确认收回
    │
    ▼
任务状态 → recalled
    │
    ├── 写入 assignment_recalls 审计表
    └── 取消相关 pending 审批记录（标记 rejected）
```

**约束**：
- 仅发起部门管理员可收回
- 已汇总（aggregated）的任务不可收回
- 已收回的任务不可重复收回
- 收回原因必填

### 6.3 一次性下发

```
下发时勾选「一次性下发」
    │
    ▼
period_label 追加唯一时间戳后缀（如 "2026年07月 #1784862420000"）
    │
    ▼
使用 INSERT（非 INSERT IGNORE）写入，is_one_time = 1
    │
    ▼
绕过 uq_assignment_period 唯一约束
```

**使用场景**：补充调查、临时加报等需要对同一分公司、同一周期重复下发的情况。

### 6.4 汇总逻辑

- 按模板 + 周期筛选下发任务
- 批量获取最新已批准填报（状态 ∈ pending_receipt / received）
- 数值字段执行 SUM / COUNT / AVG 聚合
- 明细行合并展示
- 仅已审批通过的填报计入统计
- 支持 Excel 导出（机构对比表 + 明细表 + 进度表）

## 7. 权限与安全

### 7.1 认证机制

- **密码存储**：bcryptjs 哈希，不可逆
- **Token**：JWT，24h 有效期，生产环境强制配置 `JWT_SECRET`
- **传输**：Bearer token via Authorization header

### 7.2 请求安全

- **CORS 白名单**：生产环境通过 `CORS_ORIGINS` 配置允许的源
- **请求体限制**：`express.json({ limit: '2mb' })`
- **SQL 注入防护**：参数化查询，`IN` 子句使用占位符
- **错误屏蔽**：500 错误返回通用文案，不泄露堆栈

### 7.3 并发安全

- **悲观锁**：模板/任务/填报写操作使用 `SELECT ... FOR UPDATE`
- **事务**：所有多步写操作在事务内，失败自动回滚
- **幂等性**：模板启停、状态变更检查当前状态，无变化则不写

### 7.4 数据隔离

通过 `owner_department_id` / `issuer_department_id` / `assigned_to_company_id` 三字段 + `department-policy.ts` 策略函数实现：

- 部门管理员仅访问本部门模板和本部门发起的下发任务
- 分公司用户仅访问本机构被下发的任务
- 超级管理员全局只读，不可写入

### 7.5 改进建议

- **速率限制**：当前未配置 rate limiting，建议在登录等敏感端点添加防暴力破解保护
- **审计日志**：建议扩展审计表覆盖所有状态变更操作

| 连接池 | connectionLimit=25，queueLimit=0，waitForConnections=true |
| 批量查询 | getXxxByIds + Map 关联，消除 N+1 |
| SQL 级过滤 | 聚合/历史端点在 SQL 层过滤，避免全表加载 |
| 性能索引 | 006 迁移补充 submissions/approvals 复合索引 |
| 悲观锁 | FOR UPDATE 防并发竞态 |

### 8.2 后端优化

| 优化项 | 说明 |
|--------|------|
| gzip 压缩 | compression() 中间件 |
| 认证缓存 | 30s 内存缓存，避免重复查库 |
| 异步中间件 | 全部 async/await，不阻塞事件循环 |
| 异步密码比较 | bcrypt.compare（非 compareSync） |

### 8.3 前端优化

| 优化项 | 说明 |
|--------|------|
| 代码分割 | React.lazy 9 页面 + Vite manualChunks 5 大依赖包 |
| SWR 缓存 | 6 个全局 hook，revalidateOnFocus: false |
| 条件请求 | 按角色条件加载，减少不必要请求 |
| 防重复提交 | lifecycleActionIdRef 防双击 |
